# Independent review of Baldur's collector and estimator (2026-10-03/04)

A separate reviewer, with no part in writing the code, tried to break Baldur 0.3 against the Baldur spec and proved each finding with a script it ran. It found 16 confirmed defects. Five could only make estimates too high (1, 2, 3, 4, 7); several others made numbers depend on collection order or on the range asked for. All 16 are fixed, each has a regression test in `tests/test_baldur.py`, and the reviewer's own scripts were re-run against the fixed code with the expected results. Its two randomized fuzzers (1,500 store/approval sequences; 600 float and constraint cases) report 0 problems after the fixes. The reviewer's scripts and fuzzers ran in its own session and aren't kept in the repo; each finding lives on as the regression test named below.

## Confirmed defects

| # | Defect | Fix | Regression test |
| --- | --- | --- | --- |

## Found while checking the handoff (2026-10-04)

A second agent checked `HANDOFF.md`, `AGENTS.md`, this record and the README against the code. Besides wording, it found one defect. Running the suite the way Windows does (no `time.tzset`, so in the machine's own zone) across 14 zones found a test that failed in zones from UTC+4 up to UTC+6, such as Dubai, Karachi, Kolkata and Kathmandu.

| Issue | Fix | Test |
| --- | --- | --- |
| `setup --from-git` read `git config --global`, which skips `[include]` files, so an email kept in an included file was invisible | Reads config the way git does (`git config --includes --get`); an email set per folder with `includeIf` is added with `--email` | `ReviewCollectTests.test_setup_finds_an_email_kept_in_an_included_config_file` |
| A test assumed "now + 2 h" fell on the same local day, so it failed in zones such as Asia/Kolkata (the estimator was right) | The test estimates the future commit's own day | `SessionTests.test_each_change_counts_once_and_future_commits_are_left_out`, now passing in all 14 zones |

## GitHub Enterprise Server support (0.3.1, 2026-10-04)

The spec recorded Brandon's GitHub as Enterprise Server, but the 0.3.0 code had no support for it: any remote host containing "github" counted, and only a committer named "GitHub…" from a `noreply@` address was a squash. 0.3.1 adds it: `github_api` takes the server's host and stores `https://HOST/api/v3`; only remotes on that host get `github_repo`; and a committer named "GitHub" or "GitHub Enterprise" from any address writes squash copies. A fresh reviewer then tried to break the change with scripts it ran, on Python 3.9.6 and 3.14. It compared 1,232 committer name, email and subject combinations against 0.3.0 and found no commit that 0.3.0 skipped and 0.3.1 counts. It confirmed four defects, all fixed:

| # | Defect | Fix | Regression test |
| --- | --- | --- | --- |
| 17 | Some `github_api` values raised `ValueError` from `urllib.parse` instead of a settings message, and the message repeated the address, token included; ports such as `+443` were read differently on 3.9 and 3.14 | The address is parsed by hand, and no message repeats what was typed | `EnterpriseServerTests.test_github_api_takes_the_servers_host_and_stores_its_api_address` |
| 18 | A clone kept a stale `github_repo` after switching hosts or turning GitHub off, and because the column is unique and holds no host, the server's own clone of the same owner/name couldn't get it | Before collecting, clones whose remote isn't on your GitHub lose `github_repo`; each collection sets it outright | `EnterpriseServerTests.test_only_remotes_on_your_github_are_github_repositories` |
| 19 | A `github_api` value 0.3.0 accepted (such as `http://...`) made the whole settings file "broken", stopping estimates and approvals | `github_api` never changes a number, so a bad value turns GitHub off with a warning; estimating settings still stop everything | `EnterpriseServerTests.test_a_bad_github_api_turns_github_off_not_baldur` |

| 20 | **Skipping a squash could raise a day.** A squash commit GitHub writes in the middle of your local work bridges two stretches of commits into one session longer than `max_session_minutes`; skipping it left two sessions, each under the clamp. In the reviewer's repro the day went from 4h00m to 5h00m, and a longer day from 4h00m to 8h00m. 0.3.0 already did this for github.com squashes | Copies are stored with `is_merge = 1` and no keys, never as work. Sessions they link (every step no longer than the idle gap) are one stretch: together they keep no more than the single session they'd have formed with the copy counted, and every session in the stretch is scaled by the same factor, so spans and each session's split across tickets stay what the evidence says. A copy never adds a minute | `SquashLinkTests` (5 tests, including randomized ones), `EnterpriseServerTests.test_a_squash_between_two_stretches_doesnt_raise_the_day` |

A second reviewer then tried to break the fix for #20. Its first version cut the earliest sessions of a stretch instead of scaling them, and the review confirmed ten problems with it. All but two are fixed; the remaining two are design decisions, recorded below.

| # | Defect | Fix | Regression test |
| --- | --- | --- | --- |
| 21 | Cutting a session's start left its minutes to the commits still inside it, so a ticket rose above both skipping and counting the copy (PROJ-2 from 0m to 15m); across midnight a part borrowed the next day's commit | Scale every session in the stretch alike instead of cutting | `SquashLinkTests.test_no_ticket_rises_when_copies_link_sessions`, `test_no_ticket_rises_over_random_days` |
| 22 | The cut could shrink a session to nothing: a 0-minute `work_sessions` row, "08:00-08:00" in the basis and report, and a worklog start before the time it covers | Scaling never changes a span | `SquashLinkTests.test_no_ticket_rises_when_copies_link_sessions` |
| 23 | A clone collected before a copy was recognised, and never collected again, still held the copy as work | Work (`store._MINE`) leaves out any SHA a row marks as a copy | `EnterpriseServerTests.test_a_clone_still_holding_a_copy_as_work_doesnt_count_it` |
| 24 | A local `git merge --squash` was a copy in one clone and two hours of work in a single-branch clone that can't see the commits it lists (also in 0.3.0) | A squash is a copy when the commits it lists are yours in any repository | `EnterpriseServerTests.test_a_local_squash_is_a_copy_whichever_clone_has_its_branch` |
| 25 | Stored copies showed up in `v_activity` as your commits | Muninn schema v2 (`0002_copies_arent_activity.sql`): `v_activity` leaves out `is_merge = 1`; Baldur needs v2 | `tools/check_muninn_schema.py` ("v_activity leaves out squash copies"), `test_a_squash_between_two_stretches_doesnt_raise_the_day` |
| 26 | A hand-set key on a commit later recognised as a copy survived, so Freya's commit count included it; its `patch_id` stayed | A copy keeps no keys and no `patch_id`; `cli.py keys` refuses one with a message | `EnterpriseServerTests.test_a_squash_0_3_0_stored_as_work_stops_counting` |
| 27 | After removing an email, "N commits no longer count as yours" counted copies | Copies aren't counted | `test_a_squash_between_two_stretches_doesnt_raise_the_day` |
| 28 | `github_api` accepted a host followed by a newline (`$` matches before a final `\n`), which turned every remote into a non-GitHub one | The host must match in full | `EnterpriseServerTests.test_github_api_takes_the_servers_host_and_stores_its_api_address` |

Decided, not fixed:

- **The day cap shares freed room.** When a linked stretch keeps fewer minutes on a day that hits its cap, the cap's proportional scale rises, so tickets outside the stretch can gain (PROJ-3 from 3h30m to 4h00m in the repro). The day total never rises. That's the spec's day cap (every session scaled by the same factor), and counting the copy as work gives the same result.
- **`min_session_minutes` longer than `idle_gap_minutes`.** A copy that links nothing can still, counted as work, push a too-short session's start later. Linking doesn't model that, so in this setting the fix gives what skipping gave (235 minutes where counting the copy gives 185). The defaults (15 and 120) can't reach it.

A third, narrower review then ran the revised fix against the 0.3.0 code and found nothing:

- **Direction:** 50,655 random days (127,054 proposals) with the cap off, and 151,965 with it on. No proposal and no day rose with copies.
- **Range:** no difference between estimating one day, two or three, in 11,892 random databases and around both daylight-saving changes.
- **Idempotence:** re-running stored nothing new. Hashes of unlinked proposals didn't move, except through the day cap as above.
- **Migration:** a 0.3.0 Muninn v1 database migrates to v2. Baldur refuses a v1 file with "Open Asgard to upgrade it."

Also noted: on Enterprise Server, a file edited on the website whose subject happens to end "(#N)" is now skipped as a squash, as it already was on github.com. GitHub's own subject for a web edit ("Update README.md") doesn't end that way.

## Not fixed (known limitations)

- **Midnight daylight-saving zones** (such as Asia/Beirut): SQLite and Python disagree on when such a day starts, by an hour. US zones change at 02:00, so this doesn't arise there.
- **Past-dated commits** (a wrong clock in the past) can't be told from real history and count on their date.
- **Pull request head branches** as a key source wait for the GitHub step; `keys.choose()` already accepts them.
- **Reflog entries inside a session** don't extend it; only the checkout onto the first commit's branch moves the start (a deliberate choice that biases low).
