# Independent reviews of Muninn's hardening and Baldur's GitHub keys (2026-10-06 to 10-09)

Four reviews in two rounds, each by an agent with no part in writing the code, proving every finding with a script it ran:

| Round | Target | Confirmed | Worst |
| --- | --- | --- | --- |
| 1 | Muninn hardening (schema v3, guard, scrubbing, restore, housekeeping) | 21 | A restore of the live file onto itself left no database, and the next start made an empty one |
| 1 | Baldur's GitHub 'pr' keys | 8 | A commit in two PRs flipped ticket whenever either PR was touched; an edited-title squash counted as work |
| 2 | The round-1 fixes in Muninn | 9 | One app could take over another's sync cursor; moving a posted worklog to another day in Jira posted it again |
| 2 | The round-1 fixes in Baldur | 8 | Databases upgraded from v2 never got the new PR data; a squash titled like one of its commits counted as work |

Every confirmed finding is fixed, or listed under "Open" with its reason. Each fix has a regression test in `tests/test_muninn_review.py` or `tests/test_baldur_github_review.py`, named after its id below. The reviewers' scripts were re-run against the fixed code. Results on macOS with Python 3.14 and SQLite 3.53:
- 444 tests across Odin and Asgard pass, 19 skipped.
- `tools/check_muninn_schema.py` passes 148 checks.
- `baldur_smoke.sh` still ends at PROJ-42 1h30m, PROJ-51 30m.

The scripts ran in the reviewers' sessions and aren't kept in the repo.

## Outcomes changed on purpose

Three of the reviewers' round-1 checks now report a different outcome. That is intended, not a regression:
- A failure on one PR's commits no longer throws away the rest of that repository's pass.
- Commits are fetched for every PR of yours, including ones whose head names no key. That's how the smallest-PR rule and the fall-back can judge them.
- The round-1 edited-title script predates `merge_commit_sha` in the fake server; round 2's squash scripts replace it.

## Open

- **R4: time-zone travel and hand-logged worklogs (accepted).** If the laptop's time zone changes between a worklog logged by hand (in Jira or typed into Odin) and a changed approval, that worklog can fall outside the day and the approval's shortfall is posted on top of it. Asgard runs only in US time zones (decided Oct 9), at most 6 hours apart, so this needs a hand-logged worklog within 6 hours of midnight and a move before the day's approval changes. `check` flags Baldur time above an approval; it doesn't see this case.
- **Scrub limits.** These are accepted:
  - `token=refresh` is masked (any `name=value` with a weak name is).
  - `password hunter2` (no `:` or `=`) isn't caught.
  - URL-encoded or multi-word passwords are only partly masked.

  Tokens belong in Credential Manager; scrubbing is the safety net.
- **Windows-only, not run.** Specified in [windows-lab-spec-0.4.md](windows-lab-spec-0.4.md).
  - Restore's renames while an app holds the file open: expected to fail and roll back.
  - Whether the python.org Python 3.11 build's SQLite enables defensive mode: without it apps can write the search index's internal tables, and startup now rebuilds them.
  - Schema-drift comparison on a file made by an older SQLite (3.37): FTS5's internal table definitions could differ by version.
